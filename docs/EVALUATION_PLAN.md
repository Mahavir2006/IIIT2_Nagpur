# Evaluation plan

Updated 26 October 2026.

## Checks that exist now

- `npm run verify:weather` checks Open-Meteo response mapping, 72-value coverage, Mumbai timezone normalization and malformed array rejection using a deterministic fixture.
- `npm run verify:weather-baseline` checks exact chronological origin/target alignment, weekly seasonal lag use, and missing-input skips with synthetic unit fixtures.
- `npm run ingest:weather-history -- --start=2023-01-01 --end=2025-12-31 --out=data/processed/open-meteo-era5-marine-lines-2023-2025.csv` fetches bounded yearly chunks through the server adapter and writes a normalized CSV plus manifest.
- `npm run build:weather-features -- --input=data/processed/open-meteo-era5-marine-lines-2023-2025.csv --out=data/features/era5-rainfall-features-2023-2025.csv` creates versioned antecedent-rain features and 1/6/24/72-hour future accumulation targets. Its manifest hashes both input and output and states that features stop at each prediction origin.
- `npm run evaluate:weather-baseline -- --input=data/processed/open-meteo-era5-marine-lines-2023-2025.csv --test-year=2025 --out=data/evaluation/rainfall-baseline-2025.json --public-out=public/data/rainfall-baseline-2025.json` reproduces the persistence and seven-day seasonal-naïve holdout report.
- The measured report also includes a trained ridge regression model using 2023 through 2024 for training and 2025 for testing. It fits separate horizons, uses past 1/6/24/72-hour rain totals, a previous-week target window, and local-hour/year cyclic terms; scaling statistics are fit on training only. Target windows must end before the test boundary.
- Install the audited Python dependency with `python -m pip install -r requirements-ml.txt`; then run `npm run build:weather-features` if the feature CSV is absent and `npm run evaluate:online-rainfall`. The River 0.26.1 replay is prequential, tunes an alert threshold using only the preceding 365-day stream, delays label updates until each target horizon has elapsed, and reports MAE/RMSE beside persistence/seasonal-naïve baselines. It reports raw and online-calibrated heavy-rain precision, recall, F1, FPR, FNR, Brier/ECE, confusion counts, and false-positive/false-negative examples. It also reports rolling conformal interval coverage and ADWIN drift events.
- `npm run verify:online-rainfall` tests future-label rejection, River update behavior, calibration updates, threshold selection, and minimum residual counts. The report is published as `/data/river-online-rainfall-2025.json`.
- `npm run train:synthetic-flood-model` regenerates River multi-system synthetic-surrogate coefficients at `src/server/pravaah-synthetic-flood-model.json` and a random holdout report at `data/evaluation/synthetic-cascade-model-v2.json`. The feature vector covers weather, river/soil, traffic/transit, power, hospital/EMS, satellite/geospatial, incidents and citizen reports. At inference, only rainfall is a live provider forecast; other domains are static proxies or simulated values and the API returns their provenance. `npm run verify:synthetic-flood-model` checks reproducibility, feature behavior, model metadata, missing-input handling and inference. Metrics are synthetic teacher-rule agreement only, never observed flood accuracy or warning skill.
- `npm run verify:cascade-pipeline` tests future-arrival rejection, duplicate and uncorroborated-report trust handling, late events, lagged association discovery on the synthetic replay, normalized four-state distributions at all nine horizons, monotonically cumulative critical probability, confidence-width response to data health, and budgeted/zone-targeted interventions including delay handling. `/api/pravaah/cascade` uses the same engine with 500 default rollouts and is marked `simulated_stream`.
- `POST /api/pravaah/interventions` runs the resource-constrained intervention optimizer against the same synthetic cascade snapshot. It validates the budget, action IDs, quantities, delays, and zone IDs; action ranking uses log-survival improvement so an all-India union probability near 1 does not erase local intervention benefits through floating-point saturation. The returned impact and ranking remain synthetic demonstrations, not operational recommendations.
- Current 2025 replay summary: 8,688 test origins; online rainfall MAE (mm) is 0.100/0.840/4.206/18.036 at 1/6/24/72h. Against the same-origin persistence baseline, River is better at 6h/24h, marginally worse at 1h, and worse at 72h. The calibrated 24-hour heavy-rain event classifier records 83 false negatives and 9 false positives at its validation-selected F2 threshold (recall 9.8%, precision 11.3%, FNR 90.2%). This is poor event detection and not flood prediction; retain the experiment for diagnosis, not alerting.
- The River replay's 90% nominal rolling residual intervals cover roughly 82% of this test set; this is a measured under-coverage result, not a valid 90% operational guarantee. Drift adaptation is a demonstration on historical ERA5, not proof of future adaptation benefit.
- The 2025 report is published in the Model Health route. Horizon sample counts are 8,759, 8,754, 8,736, and 8,688 for 1, 6, 24, and 72-hour windows. For ridge, measured MAE/RMSE in mm are 0.101/0.313, 0.834/2.496, 3.885/10.185, and 12.654/24.630 respectively. These evaluate one point's ERA5 reanalysis, not an independent observation or archived forecast.
- Chronos-2 is not benchmarked: its package and weights are not installed/cached in the local environment. A fair future run must use the same origin/target split and target data, log checkpoint revision, hardware, inference latency and package/model license, then compare against persistence, seasonal-naïve and ridge.
- A local smoke request to `/api/pravaah/weather` verifies live provider reachability and reports actual returned coverage at request time; it is not a forecast-skill score.
- `npm run verify:pravaah` checks deterministic rainfall propagation, graph relations, ambulance delay and reroute stages.
- `npm run verify:sim`, `npm run verify:geometry`, and `npm run verify:scenario` exercise the existing simulation and geometry code.

## Weather feed operational evaluation

For each retrieval, retain provider identity, location, request/retrieval time, hourly valid times, units, returned coverage, null count, and HTTP/provider failure state. Monitor timeout/failure rate, response latency, cache age, and unexpected coverage changes. Do not compare the provider's forecast with itself as validation.

## Future forecast skill evaluation

Acquire time-aligned archived forecasts and independent observations for the target geography. Split by held-out storm/event and chronological period to prevent leakage. Compare at each lead time with persistence and climatology; use MAE/RMSE for continuous rainfall, Brier score/reliability for threshold probabilities, and event-based precision/recall with explicit thresholds for warning use. Report spatial coverage, missing-data handling, confidence intervals across events and subgroup/season performance. Flood impact model evaluation additionally requires verified impact labels and calibrated local asset/drainage inputs.

## Release gate

The current feed is a usable forecast display, not a validated PRAVAAH warning system. Do not label it an alert or claim flood-risk prediction until independent, leakage-safe skill and impact validation are completed.
